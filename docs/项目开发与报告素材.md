# NewsBrief 项目开发与报告素材

## 一、项目概述

### 1.1 选题背景

移动互联网环境下，新闻内容数量持续增长。普通读者面对较长的政策、民生、科技和文化新闻时，往往需要在有限时间内获取事件主体、核心措施、影响范围和后续安排。传统新闻阅读工具通常只提供全文展示，缺少对重点信息的提炼与来源核验。

本项目以“自动生成新闻摘要工具”为题，设计并实现 NewsBrief 中文新闻摘要工作台。系统面向普通新闻读者，支持用户粘贴中文新闻正文，在本地生成可追溯的摘要、关键词和关键句，并提供历史保存、复制导出和结果恢复能力。

### 1.2 项目目标

1. 建立不依赖付费 API 的本地中文新闻摘要能力，确保答辩环境下稳定演示。
2. 让每个本地摘要句都对应原文中的具体句子，降低摘要结果不可核验的问题。
3. 通过响应式网页构建输入、生成、核验、保存和复用的完整阅读工作流。
4. 预留 AI 增强接口，在配置服务后提升摘要表达自然度，同时保持本地回退策略。

### 1.3 用户与需求

目标用户为需要快速理解长新闻的普通读者和学生。用户需要快速输入新闻、选择摘要长度、查看摘要依据、保存重要内容，并在后续重新检索。系统不处理新闻爬虫、链接自动解析、账号系统或云端同步，以保证第一版的稳定性和合规性。

## 二、技术方案

### 2.1 架构设计

系统由 Vue 3 前端、FastAPI 后端和 SQLite 本地数据库组成。前端负责新闻输入、结果展示、原文高亮、历史记录和设置页面；后端负责中文 TextRank 摘要、关键词提取、AI 服务调用和历史记录管理；SQLite 用于持久化用户主动保存的记录。

数据流程为：用户输入新闻正文 -> 前端调用摘要接口 -> 后端执行清洗、分句、分词、TF-IDF、句子相似度图和 PageRank -> 返回摘要与原文依据 -> 前端渲染结果 -> 用户按需保存至 SQLite。

### 2.2 技术选型理由

- Vue 3 + TypeScript：组件化清晰，适合构建多页面响应式工作台。
- FastAPI：接口定义直观、参数校验明确，便于前后端分离开发。
- SQLite：无额外服务部署需求，满足本机历史记录保存。
- jieba + scikit-learn + networkx：能够实现中文分词、TF-IDF 句子向量和 PageRank 句子重要性排序。
- TextRank4ZH：作为中文 TextRank 实现思路的参考；本项目自行实现核心算法，避免旧依赖兼容问题。

## 三、算法设计

### 3.1 本地摘要流程

1. 清洗空白符、无意义段落与重复句，限制正文为 80 至 8,000 个有效字符。
2. 使用中文标点进行分句，最多保留 180 个有效句。
3. 使用 jieba 分词并过滤常见停用词，形成句子 TF-IDF 向量。
4. 计算句子之间的余弦相似度，构建带权句子图。
5. 使用 PageRank 计算句子重要性，再通过 MMR 降低相似句同时入选的概率。
6. 按原文顺序输出选中的句子，并返回其原文索引。
7. 对选中句子的 TF-IDF 权重求和，输出关键词。

### 3.2 可追溯性设计

本地模式不生成原文之外的句子，而是只选择关键句。接口会返回 `source_sentence_ids`，前端用高亮和编号展示依据。AI 模式要求每个要点附带依据句索引；如果 AI 返回格式无效、索引越界、超时或未配置服务，系统会直接回退为本地摘要。

## 十一、V1.2 自适应与 AI 配置完善

### 11.1 自适应策略

本版本不使用不可靠的浏览器型号识别，而是同时依据可用视口宽度和输入能力自动选择布局。宽度小于 720px 时始终采用手机单列；宽度达到 720px 且检测到鼠标或触控板的精细指针时保留电脑双栏；中等宽度的纯触屏设备采用上下阅读顺序。窗口缩放、设备旋转或改变窗口大小时，系统会重新判断，无需刷新页面。

这样可以避免将高分辨率手机横屏错误当成电脑，也避免 Windows 显示缩放后仍强制采用手机布局。该策略的优先目标是保证输入区和摘要区始终可读、可点击，而不是依赖容易伪造的设备名称。

### 11.2 AI 配置与安全设计

设置页新增“AI 服务配置”表单，支持填写 API Key、兼容服务地址和模型名称，默认值为 DeepSeek 的 `https://api.deepseek.com` 与 `deepseek-chat`。用户点击“保存并启用”后，前端仅通过当前本机连接把数据传给后端；后端校验地址格式、模型名称与换行字符后，将配置写入被 Git 忽略的 `backend/.env`，并立即更新当前进程。

接口只返回 AI 是否可用、服务地址和模型名称，不会返回 API Key；密钥也不写入浏览器存储、SQLite 历史、日志或导出文件。配置完成后，工作台中的“AI 增强”按钮自动启用；调用失败时仍回退到可追溯的本地摘要。

## 十二、V1.3 可信阅读体验升级

### 12.1 改进原因

V1.2 已经具备完整的摘要闭环，但宽屏工作台的正文输入区域偏高，摘要控制常落在首屏之外；空状态和历史页也存在较多无效留白。与此同时，系统虽能返回原文依据，却没有直接告诉用户摘要依据是否完整、关键句之间是否存在重复风险。V1.3 因此从“功能可用”转向“阅读可信、操作紧凑、状态可解释”。

### 12.2 摘要质量指标

接口在原摘要结果之外返回 `quality` 对象，用于展示可解释的辅助指标，而非宣称摘要绝对正确。

| 指标       | 计算方式                                     | 用户含义                       |
| ---------- | -------------------------------------------- | ------------------------------ |
| 依据完整度 | 有效原文句索引的要点数 / 全部要点数          | 判断每条要点是否具备原文支撑   |
| 重复风险   | 已选句或 AI 要点之间的最大 TF-IDF 余弦相似度 | 数值越低，摘要内容越不容易重复 |
| 关键句数量 | 选中的原文句数 / 有效原文句数                | 了解摘要覆盖的原文规模         |
| 处理耗时   | 后端从接收文本到返回结果的毫秒数             | 观察本地处理响应情况           |

本地 TextRank 直接复用已构造的句子相似度矩阵计算重复风险；AI 模式对生成要点再次计算词汇重合度，并继续校验所有依据句索引。质量指标与原文依据标签共同构成结果的可解释性证据。

### 12.3 AI 配置验证

新增 `POST /api/ai-config/verify`。该接口接收当前表单中尚未保存的 Key、服务地址和模型名称，仅在用户点击“测试连接”时发起极小请求，不写入 `.env`、SQLite、日志或导出文件。响应只包含是否可用、模型名称和安全的错误说明；认证失败、服务或模型不存在、超时等情况均不会返回密钥。

设置页将“测试连接”和“保存配置”拆分。测试成功只说明连接可用，用户仍需主动点击“保存配置”才会写入本机 `backend/.env`。这使得课程答辩可在未配置 Key 的情况下完整演示本地模式，也可安全展示 AI 的加分能力。

### 12.4 视觉与响应式优化

界面采用雾白背景、深墨文字、珊瑚红主操作、青绿色可信状态和琥珀色 AI 状态。取消厚重阴影与装饰性渐变，统一为 6 至 8px 圆角、细边框和轻量悬停反馈。桌面端输入框限制为 `clamp(270px, 32vh, 360px)`，确保生成控制在常见 1440px 宽度首屏可见；样例库改为浮层，避免展开后推挤页面。

## 十三、V1.4 新闻感知摘要与长度对比

### 13.1 本版本目标与设计取舍

通用 TextRank 主要依据句子之间的关联度排序，能够识别被多处讨论的内容，但对中文新闻常见的“标题提示主题、导语概括事件、数字说明事实”结构利用不足。V1.4 不引入预训练模型、新闻爬虫或云端依赖，而是在现有本地抽取式算法上增加轻量新闻规则，使结果更贴近新闻阅读的重点，同时保留每一条摘要都可回到原文核验的特点。

本版本还增加了本地三档长度对比。用户不必为简短、标准或详细摘要重复发起三次生成，可以在同一份文本分析结果上比较三种阅读长度，再决定复制、导出或保存哪一个版本。该功能只处理内存中的当前内容，不会调用 AI，也不会新增 SQLite 历史记录，因此不会产生额外费用或污染历史数据。

### 13.2 新闻感知排序算法

在完成清洗、中文分句、jieba 分词、TF-IDF 句向量、余弦相似度图和 PageRank 后，系统将各项信号归一化并计算本地排序分数：

| 信号            | 权重 | 计算方式                                     | 设计目的                       |
| --------------- | ---: | -------------------------------------------- | ------------------------------ |
| PageRank 重要性 |  70% | 句子在 TF-IDF 相似度图中的归一化 PageRank    | 保留全文共同关注的核心事实     |
| 标题相关度      |  14% | 标题有效词与句子有效词的重合比例             | 使摘要围绕新闻主题而非局部细节 |
| 导语位置        |  10% | 按原文位置从前向后递减                       | 适度保留新闻导语中的事件概况   |
| 数字事实        |   6% | 识别日期、时间、金额、比例、人数、数量等表达 | 优先覆盖可核验的新闻事实       |

当用户不填写标题时，原本的 14% 标题权重会并入 PageRank，使中心性权重为 84%，避免虚构或猜测新闻主题。融合排序后仍使用 MMR（最大边际相关性）选择低重复的关键句，并按照原文顺序拼接；关键词、句号索引、原文定位和质量指标均继续复用原有结果结构。

可直接用于报告的算法说明如下：

“本系统采用新闻感知的抽取式摘要方法。首先以 TF-IDF 句向量和 PageRank 建立新闻的全局重要性排序；随后融合标题词重合、导语位置和数字事实三类新闻结构信号。该策略既避免单纯按照首段截取，也不依赖外部生成式模型。最后通过 MMR 抑制相似句重复，并将入选句映射回原文索引，实现摘要结果的可追溯验证。”

### 13.3 一次分析、三次生成的内部流程

为避免长度对比重复执行计算量较大的分析步骤，后端将本地摘要拆为两个阶段：

1. `NewsAnalysis` 一次性完成文本清洗、有效句筛选、分词、TF-IDF、相似度矩阵、PageRank、融合排序和关键词权重计算。
2. `summarize()` 根据一个长度档位执行 MMR 选句并组装结果；`compare_summaries()` 对同一份 `NewsAnalysis` 分别生成简短、标准和详细结果。
3. 每个结果仍返回摘要文本、要点、关键词、原文句索引、压缩率、处理耗时和 `quality` 指标，前端无需采用特殊的数据结构处理。

这一设计使对比操作不会重复分句和建图，也确保三档摘要基于完全相同的原文分析条件，具有可比较性。

## 十五、V2.0 竞赛级可信新闻 AI 升级

### 15.1 项目定位与设计原则

V2.0 将产品定位为“可追溯、可核验、可协作的中文新闻理解工作台”。系统的竞争点不在于简单调用生成式模型，而在于让摘要中的每一条信息都能回到原文核验，并让使用者能够基于原文证据调整本地摘要。离线本地算法仍是完整演示的主路径；AI 仅为可选增强，连接失败时自动回退至本地结果。

本版本继续明确不做新闻爬虫、账号、云同步、批量处理、模型训练和多媒体摘要。这些功能虽然能扩大产品范围，却不能直接提升摘要的可靠性、可解释性或课程项目的离线可演示性。

### 15.2 六要素事实与事实覆盖约束

系统在本地文本分析完成后，以可解释规则提取主体、时间、地点、核心事件、关键数值、影响或后续六类事实。每个事实卡固定返回事实类型、展示标签、原文片段、依据句索引和 `local_rule` 方法标识。规则无法确认的信息直接缺失，不会根据常识补写。用户点击事实卡会自动进入“原文依据”标签并定位对应句子。

在原有新闻感知排序的基础上，选句阶段采用以下评分：

`选句得分 = 0.72 × 新闻重要性 - 0.20 × 与已选句最大相似度 + 0.08 × 未覆盖事实收益`

其中新闻重要性仍由 70% PageRank、14% 标题相关度、10% 导语位置和 6% 数字事实信号组成；未填写标题时，标题权重并入 PageRank。事实收益只奖励尚未被已选句覆盖的事实类别，因此不会把“事实覆盖率”误写成绝对真实性。

| 指标         | 定义                                          | 解释边界                                             |
| ------------ | --------------------------------------------- | ---------------------------------------------------- |
| 事实覆盖率   | 被摘要选句覆盖的事实卡数量 / 已发现事实卡数量 | 只表示本地证据覆盖，不证明新闻事实本身真伪           |
| 已发现事实数 | 规则成功识别且有依据句的事实卡数量            | 规则未识别不代表新闻中不存在该要素                   |
| 已覆盖事实数 | 至少有一个依据句被摘要选择的事实卡数量        | 用于观察摘要是否遗漏已发现的重要信息                 |
| 重复风险     | 已选句最大 TF-IDF 余弦相似度转换为 0–100      | 数值越低表示词汇重复风险越低，不等同于语义完全不重复 |

### 15.3 证据链协作与历史可复现

本地模式的“原文依据”提供固定句和排除句操作。固定句必须保留在摘要中，排除句不会进入结果；同一句不能同时拥有两种状态。系统会在请求前和后端两层校验重复索引、冲突索引、无效句、固定句超出当前长度、排除全部候选句等情况，并返回可理解的错误提示。

约束同时作用于单次摘要和三档长度对比。用户选择某一对比结果后，复制、导出、保存历史和原文高亮均基于该结果。SQLite 历史记录新增 `facts_json` 与 `constraints_json`，通过非破坏性迁移兼容旧记录；恢复历史时会重新呈现事实卡、证据状态和最终摘要。AI 模式展示同一份本地事实卡，但不开放证据句编辑，避免将生成文本与本地证据链混为一谈。

### 15.4 可复现评测与数据伦理

评测体系设计为本地私有新闻测试集：校园、民生、政策、科技、财经、文化各 10 篇，共 60 篇。每篇记录标题、来源链接、发布日期、采集日期、内容哈希与使用说明；正文快照、关键句标注、参考摘要、事实标注和盲评原始评分仅保存在被 Git 忽略的 `backend/benchmark_private/` 目录。仓库公开数据元数据结构、标注规范、评测脚本与汇总格式，不公开转载新闻正文。

自动评测统一比较 Lead-3、基础 TextRank、V1.4 新闻感知算法和 V2.0 事实覆盖算法，计算关键句 F1、事实覆盖率、数字事实召回率、重复风险、压缩率、平均耗时与 P95 耗时。各基线均由自身选句重新组装摘要文本、要点、原文选中态、关键词与质量指标，不能复用 V2.0 的结果外壳。人工盲评计划使用 24 篇均衡新闻、5–8 名评测者，并对事实忠实度、关键信息覆盖度、阅读清晰度、可信感四项按 1–5 分评分；报告应同时呈现均值、中位数、离散度与 95% Bootstrap 区间。

**当前真实状态：** 评测接口、标注结构、隐私边界、四种算法运行器和可信度实验室页面已经实现；真实 60 篇合规新闻快照、双人复核标注与 5–8 人盲评数据尚未采集，因此目前不展示或宣称任何算法优越结论。完成数据采集并运行评测后，才可以在报告中填写真实汇总数值。

## 十六、V2.1 新闻核验线索与公开来源交叉核验

### 16.1 设计目标与边界

V2.1 不将摘要系统包装成“真假新闻裁判”。新闻真实性往往依赖完整语境、持续报道、权威机构调查和人工编辑判断，单次网页检索不能替代事实核查。因此，本版本把能力定位为“核验线索”：帮助用户把输入新闻拆成可回溯的主张，展示这些主张的原文依据，并在用户主动授权联网后提供公开来源的交叉阅读线索。系统固定声明“证据状态不等同于新闻真实性结论”。

### 16.2 核验流程与方法

摘要完成后，系统复用六要素事实提取结果，构造 1 至 5 条主张。核心事件为必选项；主体、时间、地点、关键数值和影响/后续只在原文已经存在且有句索引时生成。每条主张都保留 `source_sentence_ids`，因此用户可从“核验线索”一键跳转到“原文依据”。

未配置搜索服务或用户尚未点击联网按钮时，系统返回离线主张，状态为“未联网核验”。配置 Brave Search API 后，用户主动点击“开始联网核验”才会触发外部请求。后端只构造主体、事件、时间、数值等短查询组合，不发送整篇新闻正文；每次最多 3 个查询、读取 8 条搜索结果、分析 6 个去重来源，总任务超时为 20 秒。

来源内容进入匹配前需通过 HTTPS、域名/IP、重定向、内容类型与 1.5MB 响应大小校验。系统拒绝 localhost、环回地址、私有 IP、非 HTTP(S) 协议和超过三次的跳转，以避免服务器端请求伪造风险。正文由 BeautifulSoup 提取后，使用词项覆盖与关键限定项比对进行确定性匹配；AI 不参与真假判断。相同新闻内容哈希的结果在内存中缓存 10 分钟，不持久化缓存。

### 16.3 证据状态与来源治理

| 证据状态   | 判定规则                                                   | 展示含义                       |
| ---------- | ---------------------------------------------------------- | ------------------------------ |
| 已支持     | 至少一条高可信来源覆盖主体、事件及已有的关键时间或数值限定 | 该主张获得较完整的公开来源支撑 |
| 部分支持   | 来源主题相关，但只覆盖部分限定信息                         | 需要继续查阅原始来源           |
| 待补充     | 未找到足以支撑主张的高可信来源                             | 当前检索范围内证据不足         |
| 存在冲突   | 高可信来源在相同主体和事件上出现明确时间、数值或状态矛盾   | 需要人工比较原始报道与语境     |
| 未联网核验 | 未配置 Key、用户未发起检索或网络不可用                     | 仅展示本地原文依据             |

来源按 `official`、`established_media`、`other` 三档展示。政府、公共机构和高校官方站点归为官方来源；新华社、人民网、央视、中国新闻网等明确名单归为主流媒体；其他站点仅作为阅读线索，不可单独产生“已支持”或“存在冲突”状态。历史记录只保存主张、状态、来源 URL、域名、标题、短摘录、检索时间与内容哈希，不保存远程网页全文。

### 16.4 可直接用于报告的实现说明

“为避免将信息检索能力误写为自动事实裁决，系统将输出限定为可解释的证据状态。首先，系统从输入新闻中抽取带句号索引的主体、事件、时间、地点、数值和影响要素，并组合为可核验主张。其次，在用户主动触发联网核验且已配置正规搜索服务的前提下，系统仅提交最小化短查询，经过来源安全校验、站点分级和确定性词项匹配后，再返回支持、部分支持、待补充或冲突等线索。所有主张和外部证据均可回到输入原文或打开公开链接复核；系统不宣称能够直接判定新闻真实与否。”

## 十七、V2.2 AI 辅助证据解读

### 17.1 设计目标

V2.2 的目标不是让大模型替代新闻核验，而是在用户完成公开来源检索后，辅助比较“主张、来源摘录与规则状态”之间的关系。系统将规则引擎产生的证据状态保留为正式状态；AI 只能生成独立的建议状态、理由和来源编号。页面始终提示“AI 建议仅辅助阅读，不构成新闻真实性结论”。

### 17.2 数据边界与安全约束

AI 只能由用户主动点击调用，不会自动随联网核验执行。请求仅包含当前核验的主张，以及最多 6 条来源的标题、域名、等级和不超过 280 字的摘录；不包含新闻正文、完整网页内容、搜索 Key 或 AI Key。提示词将来源摘录定义为不可信数据，要求模型忽略其中任何指令，禁止搜索网络、补充外部事实、生成网址或裁决新闻真伪。

模型返回后，后端验证每一条建议：必须覆盖且只能覆盖当前主张；引用的来源编号必须存在；`已支持`、`部分支持`、`存在冲突`必须有来源引用；其中`已支持`和`存在冲突`至少引用官方或主流媒体来源。未通过验证、模型超时、鉴权失败或 JSON 格式错误时，系统仅提示 AI 解读不可用，原规则核验结果不会被修改。

### 17.3 功能实现说明

工作台在联网来源可用时显示“AI 解读证据”操作。AI 建议显示在对应主张卡内部，包含建议状态、80 至 180 字理由和可点击的来源编号；点击编号会定位到下方来源卡。重新生成摘要、加载新样例或重新联网核验时，会清除旧建议以防止证据错配。AI 建议随 `verification_json` 保存，恢复历史时可以复现，不会自动重新调用模型。

可直接用于报告的说明如下：

“系统采用规则核验与 AI 辅助解读相分离的双层设计。规则层负责来源安全校验、站点分级和主张覆盖判定，作为可复现的正式证据状态；AI 层仅在用户主动操作后，根据已获得的来源短摘录输出带来源编号的阅读建议。后端对模型输出执行主张全覆盖、引用存在性和高可信来源约束校验，任何模型异常均不会改变规则核验结论。该设计利用大模型的中文语义理解能力，同时避免将生成式模型输出误写为新闻真实性裁决。”
